# 문의 자동 분류·검수 파이프라인 (데모)

웹훅으로 받은 고객 문의를 유형별로 분류하고, **확신이 낮거나 돈·분쟁이 걸린 문의는 사람 검수로 보내고**,
실패하면 재시도·알림을 남기고, 처리 결과를 요약 보고하는 자동화 데모입니다.

> **범위를 먼저 밝힙니다.**
> - 문의 문장과 정답은 **데모용으로 생성한 가짜 데이터**입니다(생성형 AI Claude로 만들었고, 정답 라벨은 생성 시 부여). 실제 서비스에서 운영한 것이 아닙니다.
> - 외부 시스템(쇼핑몰, 문의 도구)과의 실제 연동은 구현하지 않았습니다. 웹훅을 **받는 서버**까지입니다.
> - LLM 분류·답변 생성은 구현하지 않았습니다(`llm_client.py`에 연결 자리만 있음).

## 처리 흐름
```
웹훅 수신 → 입력 검사 → 분류(일시 오류는 재시도) → 라우팅 → 비용 기록 → 일일 보고
```

| 결과 | 조건 |
|---|---|
| processed (자동 처리) | 신뢰도 0.7 이상이고 환불·클레임이 아님 |
| needs_review (사람 검수) | 환불·클레임 유형 / 신뢰도 낮음 / 빈 문의·2,000자 초과 / 분류기 출력 형식 오류 |
| failed (실패 + 알림) | 재시도 3회 모두 실패 / 예상 못 한 오류 |

## 설계 결정
- 같은 `external_id`가 다시 오면 다시 처리하지 않고 `duplicate: true`로 응답합니다(웹훅은 재전송될 수 있음).
- 일시 오류(타임아웃 등)만 재시도하고, 예상 못 한 오류는 숨기지 않고 실패로 기록해 알립니다.
- 분류기(LLM)의 출력은 믿지 않고 형식·범위를 검증합니다. 틀리면 재시도하지 않고 사람이 확인합니다.
- 모든 단계가 `logs` 테이블에 남아, 문제가 생기면 `GET /inquiry/{id}/logs`로 원인을 추적합니다.
- 환불·클레임은 신뢰도가 높아도 사람이 봅니다. 오분류의 비용이 크기 때문입니다.

## 평가
- 데이터: 데모 문의 100건 = **dev 60건**(규칙을 고치는 데 사용) + **holdout 40건**(보강이 끝난 뒤 한 번만 평가). 파일: `labeled_100.csv`
- 지표: 분류 정확도 / **자동 처리 중 정답률**(자동화가 사고를 내지 않는지) / 사람 검수 비율(자동화가 일을 얼마나 줄이는지)

### 규칙 기반 분류 보강 전후
| | 분류 정확도 | 자동 처리 중 정답 | 사람 검수 |
|---|---|---|---|
| dev 60건 | 62% → 92% | 18/20 → 30/30 | 67% → 50% |
| holdout 40건 | 60% → 80% | 12/12 → 17/17 | 70% → 57% |

dev 수치는 고친 데이터로 잰 값이라 참고용이고, 판단은 holdout으로 합니다.

### 분류 방식 비교 (holdout 40건, 규칙은 보강 전 기준)
| | 분류 정확도 | 자동 처리 | 그중 정답 | 사람 검수 |
|---|---|---|---|---|
| 규칙 기반 | 60% | 12 | 12 | 70% |
| TF-IDF + 로지스틱 회귀 | 30% | 0 | 0 | 100% |
| SBERT 임베딩 + 로지스틱 회귀 | 55% | 13 | 10 | 68% |

- 학습 모델은 dev 60건으로만 학습했습니다(유형 7개, 유형당 약 8건).
- SBERT는 규칙과 정확도가 비슷했고, 자동 처리 13건 중 3건이 틀렸습니다(확신하며 틀림). 학습 데이터가 부족해 규칙 기반을 넘지 못했습니다.
- TF-IDF는 확신이 전부 기준선(0.7) 아래라 모든 문의가 사람에게 넘어갔습니다. 안전장치는 작동했지만 자동화 효과는 없었습니다.

## 발견한 오류 사례
**확신하면서 틀린 자동 처리.** 규칙은 키워드가 한 유형에만 걸리면 신뢰도 0.9를 줍니다. 그 결과:
- "배송기사가 욕을 했습니다 사과받고 싶습니다" → `배송`(0.9)으로 **자동 처리**됐습니다. 정답은 클레임입니다. "배송"이라는 단어 하나에 걸려서입니다.
- "택배 기사님이 물건을 문 앞에 던져 놓고 가셨어요", "상품이 깨진 채로 도착했어요" 도 같은 이유로 배송 자동 처리였습니다.

**보강.** 클레임 단서(욕, 던져, 깨진, 찢어, 협박, 신고, 사기 등)를 규칙에 추가했습니다. 이제 이 문장들은 배송과 클레임이 동시에 걸려 신뢰도 0.5가 되고 **사람 검수로 넘어갑니다.** 분류 라벨은 여전히 `배송`이지만, 틀린 채로 자동 처리되는 사고는 막았습니다.
또 "사진 속 모델이 입은 **사이즈**가 뭔가요"가 교환으로 자동 처리되어 `사이즈`를 교환 키워드에서 뺐습니다(→ 기타, 검수).

## 한계
- 데이터가 100건(생성한 가짜 데이터)이고 holdout이 40건이라 1건이 2.5%p입니다. 수치는 경향으로만 읽어야 합니다.
- holdout 문장도 같은 작성자가 만들어 말투를 알고 있어, 80%는 낙관적일 수 있습니다. 독립 데이터로 다시 검증하지 않았습니다.
- 분류 유형 7개, 환불·클레임을 위험 유형으로 둔 것, 신뢰도 기준 0.7은 모두 **가정**입니다. 실제로는 담당자와 정하고 정답이 달린 데이터로 검증해야 합니다.
- 규칙은 키워드가 없는 문장을 거의 못 잡아서 검수 비율이 57%입니다(자동화가 줄인 일은 43%).
- 웹훅 서명 검증·인증이 없고, 문의를 서버에서 동기로 처리합니다(요청이 몰리면 느려짐).

## 실행
```
pip install -r requirements.txt

python simulate.py                       # 정상·실패 사례를 섞어 돌려 보기 (서버 불필요)
python -m pytest -q                      # 테스트
python evaluate.py labeled_100.csv dev   # 평가 (dev | holdout)
python compare.py                        # 분류 방식 비교 (SBERT는 설치돼 있을 때만)
python -m uvicorn app:app --reload       # 웹훅 서버 → 브라우저에서 http://127.0.0.1:8000/docs
```
서버 테스트는 `/docs` 화면에서 `POST /webhook/inquiry`에 아래를 보내면 됩니다.
```
{"external_id": "A1", "text": "택배가 언제 도착하나요?"}
```
같은 `external_id`를 다시 보내면 `duplicate: true`로 응답합니다.
